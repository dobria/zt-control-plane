# Operations

This is the practical guide for running ZT Control Plane after the container is
up. It follows the same path most people take: connect a controller, find the
right network or node, make a change, and know how to recover if something goes
wrong.

## Your first ten minutes

1. Start the Compose service.
2. Read the generated setup token from the application log (or use the value
   supplied as `APP_SETUP_TOKEN`), then open `/setup` and create the first
   administrator.
3. Add and test a remote controller connection.
4. In optional embedded mode, the local controller appears automatically and
   can be selected instead.

## Connect your controllers

### Remote ZeroTier One

Provide a name, the Service API base URL, and its `authtoken.secret` value. The API must be reachable from the application container. Prefer HTTPS through a private reverse proxy when it is not on the same host.

Private Docker, LAN and ZeroTier addresses are supported intentionally. Cloud
metadata, link-local, unspecified, multicast and reserved addresses are rejected
both when entered directly and after DNS resolution. Controller adapters never
follow HTTP redirects while carrying API credentials, and provider responses
are time- and size-bounded. Disabling TLS verification should be limited to
explicitly trusted private networks and recorded as an operational exception.

### MikroTik RouterOS

Enable RouterOS REST API access, create a dedicated least-privilege RouterOS user, and provide the HTTPS base URL, username, and password. Keep TLS verification enabled. RouterOS exposes ZeroTier only on supported hardware/package combinations.

One RouterOS connection may contain multiple ZeroTier instances with arbitrary
names. Open **Node management**, select an instance, and manage its name, UDP
port, RouterOS interface binding, route distance, enabled state, client
networks, and peers. Creating a controller network from **Networks** also
requires an instance selection. Instance identities are generated by RouterOS;
private identity material is never returned to the browser or Diagnostics. The
instance editor discovers the router's current interfaces for selection and
shows only the safe node ID, public identity, runtime state, and reported moon
roots. If the least-privilege RouterOS account cannot read `/interface`, the
editor falls back to manual interface names without blocking management.

The selected instance opens a role-based workspace. **Controlled networks**
represents its controller role, **Joined networks** represents its client role,
**Peers** shows runtime connectivity, and **Settings** contains instance-level
configuration and safe identity data. The selected instance and workspace tab
are stored in the page URL, so browser refresh and direct links retain the same
context.

RouterOS controller members are stored below `/zerotier/controller/member`.
The network screen resolves RouterOS's network-name reference back to the
16-character ZeroTier Network ID and supports add, read, edit, authorize,
enable/disable, bridge permission, one managed IP address, comment, and remove.
The RouterOS comment is provider configuration; **Control plane notes** remain
private metadata in this application.

The parent `/zerotier/controller` record is the controlled virtual network.
Its editor covers the RouterOS name, comment, enabled state, privacy, broadcast,
MTU, multicast limit, IPv4 pool, IPv6 assignment modes, and managed routes.

Editing a RouterOS joined network also exposes the supported interface settings:
enabled state, optional comment, interface name, VRF, ARP timeout, running-check
behavior, and the three ZeroTier route-acceptance switches. VRF choices are read
from `/ip/vrf`; `main` remains available if that auxiliary read is not permitted.
Interface type, MTU, actual MTU, MAC address, and runtime status are displayed as
provider-reported values rather than submitted as configuration.

### New Central

Create a New Central service account and API token, then provide the token and
organization ID. Open **Groups** on its controller card to list, create, edit,
select or delete network groups. A selected group is required for network
creation. New Central API/service accounts require an eligible Central plan.

### Legacy Central

Provide a personal Legacy Central token. The default API URL is
`https://api.zerotier.com/api/v1`.

Use **Test connection** before making operational changes. Adding or removing a
controller entry only changes this application's connection list; it does not
reconfigure the external device by itself.

## Find and manage client nodes

Use the global **Nodes** page to search identities across every controller and
network. **Network nodes** includes Central members and shows authorization,
network and controller counts. **Managed endpoints** contains only registered
Service API or RouterOS connections that the application can configure directly.

Open **Node** from an optional Embedded ZeroTier One, Remote ZeroTier One or
MikroTik controller card. The associated node connection is created
automatically from that controller connection and is used for joined networks,
client policies, peers, diagnostics and moons. New Central and Legacy Central
do not expose client Service API access, so their devices remain under each
network's **Members** tab.

## Everyday network and member work

- The global **Networks** page searches every controller and keeps filters and pagination in the URL. A controller card opens the same page pre-filtered to that controller.
- Network create/update/delete operations are sent immediately to the controller explicitly shown by the network route or creation dialog.
- Member authorization changes take effect when the managed device receives the updated network configuration.
- **Delete member** removes only the membership record. If the client is still joined, it may reappear as unauthorized.
- **Leave network** acts on the node opened from the controller card, not on an arbitrary network member.
- Destructive actions require a confirmation in the UI and are recorded in the audit log.

## Flow Rules

ZeroTier One controllers support three editing levels:

1. service templates for common allow-list policies;
2. a custom rules source editor with compiler diagnostics;
3. raw rule JSON, tags, and capabilities for advanced configuration.

The compiler must succeed before compiled rules are submitted. Keep a backup before replacing an established ruleset: a valid but overly restrictive rule can block traffic across the network.

MikroTik's controller API does not expose ZeroTier Flow Rules, tags, or capabilities, so those controls are unavailable when a MikroTik controller is selected. New Central Flow Rules also depend on provider plan entitlements.

## Backup and restore

The UI export contains an allowlisted, portable network configuration, local UI
metadata, and member configuration for the selected controller. It excludes raw
provider payloads, application users and all credentials.

Restore first produces a dry-run plan showing create/update operations. It never deletes networks that are absent from the backup. After reviewing the plan, an administrator or operator can apply it.

For complete disaster recovery, back up the Docker volume. A consistent backup is best taken from a storage snapshot or while the service is stopped by the operator. No automated stop or removal operation is included in this project.

## Keep an eye on things

- `GET /api/health` returns `200` when SQLite is available. In embedded mode it
  additionally requires the local ZeroTier token and controller API.
- The container has a Docker health check with a 30-second startup grace period.
- **Diagnostics** shows structured controller, node, peer, path, interface and
  RouterOS information. The provider payload remains available under **Raw
  provider response** for advanced troubleshooting after common credential and
  private-identity fields have been recursively redacted.
- **Audit** records management requests with user, controller or node, target, result, and timestamp. The history is paginated and can be filtered by text, result, action, actor, endpoint, and date range. Administrators can export the current filtered result as CSV; auditor accounts can inspect but cannot export the log. Secrets and password values are not written to the audit detail.

Operational pages refresh automatically while visible and when the browser regains focus. Global inventories use the last successful sanitized SQLite snapshot when a provider is unavailable and label those rows as cached. Network configuration refresh is paused while a draft contains unsaved changes, preventing background data from replacing operator input. Inventory filters, pagination and the active network tab are persisted in the page URL.

## Settings and profiles

Administrators use **Settings** to choose the live refresh interval, set the
lifetime of newly created sessions, define audit retention, restrict web access
by IP address, and manage users and roles. Audit retention is enforced when the
next audit event is written; choosing **Forever** disables automatic expiry.

The optional IP access list accepts exact IPv4 and IPv6 addresses or CIDR
networks. It requires `TRUST_PROXY=1` behind a trusted reverse proxy, and the
administrator's detected source address must match a rule before activation.
The restriction covers login, UI, and API requests; `/api/health` remains
available for Docker and container platforms. Use `IP_ALLOWLIST_BYPASS=1` only as a temporary
recovery measure after an upstream address or proxy change, then correct the
list and disable the bypass again.

Every user can open their avatar to edit their own name and email, choose the
page shown after sign-in, reduce interface motion, or change their password.
Changing a password or email requires the current password and signs the account
out on all devices. Role and account-status changes remain administrator-only.

### Two-factor authentication

Each user can enable TOTP from **Profile → Two-factor authentication**:

1. Confirm the current password.
2. Scan the locally generated QR code with Google Authenticator or another TOTP app.
3. Enter the displayed six-digit code to finish enrollment.
4. Store the ten one-time recovery codes outside the control-plane volume.

Enabling or disabling 2FA revokes all sessions and requires a new sign-in. A
recovery code can replace the authenticator code at login and is invalidated
immediately after use. Users can replace all remaining recovery codes from
their profile after confirming both their password and a second factor.

An administrator can see 2FA status under **Settings → Users & roles** and reset
2FA for another locked-out user. This deletes the authenticator secret and
recovery codes and revokes that user’s sessions. Administrators cannot use this
shortcut for their own account.

## Update without surprises

1. Back up `/data`.
2. Read the GitHub Release notes, compatibility boundaries, and known issues.
3. Update `CONTROL_PLANE_IMAGE` or `compose.release.yaml` to the new immutable
   version or published digest. Source-build operators should review the pinned
   versions in `package.json` and `Dockerfile`, run `npm run check`, and rebuild.
4. Deploy the new standard image against the same persistent volume.
5. Confirm `/api/health` and one read operation on each external connection.
6. In embedded mode, also confirm the local controller and node status.

Do not replace the volume during a routine upgrade. It contains the application
database and secrets and, in embedded mode, the controller identity.
